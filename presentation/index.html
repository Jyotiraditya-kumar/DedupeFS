Motivation & Problem Definition

Storage Redundancy & The Fundamental I/O Bottleneck

The Redundancy Problem

1. Storage Overhead from Duplicate Files:

Across user home directories, software repositories, and dataset storage, duplicate files consume 20% to 50%+ of physical disk capacity.

2. Intractability of Naive Pairwise Checks:

Directly comparing all file pairs requires O(N²) comparisons. For 50,000 files, this requires >1.2 billion pairwise checks, causing severe disk thrashing.

3. I/O Bottleneck of Unfiltered Hashing:

Computing full cryptographic digests (SHA-256) on every file forces the OS to read gigabytes of data from disk, even though most files have unique sizes.

DedupFS System Design Principles

1. Multi-Tier I/O Pruning Hierarchy:

Tier 1 size grouping eliminates ~25-40% of unique files in O(1) time with 0 disk reads. Tier 2 tests 4KB Murmur3 prefix hashes to discard header mismatches early.

2. Probabilistic Bloom Filter Pre-Check:

A dynamically sized bitset using Kirsch-Mitzenmacher double-hashing eliminates non-duplicate candidates in memory with Zero False Negatives (FN = 0).

3. Inverted Chained Hash Table:

Indexes duplicate candidates into equivalence classes in memory, enforcing load factor λ ≤ 0.75 via dynamic capacity doubling for amortized O(1) lookups.

4. Merkle Trees & Binary Max-Heap:

Merkle trees enable O(1) subtree duplicate detection and O(log N) change sync; binary Max-Heap prioritizes high-payoff clusters via Pareto 80/20 ranking.

Advanced Data Structure 1

Probabilistic Membership: Optimal Bloom Filter

Mathematical Foundation & Sizing

Optimal Bitset Sizing (m):
m = - (n · ln p) / (ln 2)²

For n = 100,000 files and p = 0.01 (1%), m = 958,506 bits (117 KB RAM).

Optimal Hash Probes (k):
k = (m / n) · ln 2 ≈ 7 probes
Kirsch-Mitzenmacher Double-Hashing:
g_i(x) = (h1(x) + i · h2(x)) mod m

Two 64-bit words from SHA-256 simulate k independent probes in O(1) CPU operations.

Zero False Negatives Invariant (FN = 0):

If any bit in g_i(x) is 0, the key was never inserted. Guaranteed no duplicate missed.

Telemetry & Empirical Validation

Memory Footprint:

Consumes only 117.0 KB of memory for 100,000 files (1.17 bytes per file), fitting entirely in CPU cache.

Observed Saturation (Fill Ratio):

Fill ratio remains at ~1.46% on benchmark corpus, well below the 50% critical threshold where false positives escalate.

Empirical False Positive Rate:

Empirical FPR = 0.00% across all benchmark tiers (0 observed false positives among 5,104 queries).

Advanced Data Structure 2

Primary Inverted Index: Chained Hash Table

Table Architecture & Rehashing

Separate Chaining Buckets:

Array of linked collision lists storing DuplicateGroup records mapping 256-bit digests to file lists.

Dynamic Rehashing Expansion:

When load factor λ = N / capacity exceeds 0.75, capacity doubles (4,096 → 8,192...) and rehashes all elements in amortized O(1) time.

Bitwise Power-of-Two Indexing:
bucket_idx = hash(key) & (capacity - 1)

Avoids expensive modulo (%) division on modern CPUs.

Empirical Table Telemetry

Allocated Buckets & Elements:

4,096 allocated buckets storing 2,012 distinct file equivalence classes.

Operating Load Factor (λ):

Current λ = 0.491 (≤ 0.75). Guarantees average lookup time O(1 + λ/2) ≈ 1.25 memory accesses.

Max Chain Length & Variance:

Max chain length = 4; average non-empty chain length = 1.26. Variance < 0.05 indicates uniform bucket spread.

Advanced Data Structure 3

Hierarchical Cryptographic Merkle Hash Tree

Tree Construction & Cryptography

Cryptographic Hierarchy:

Leaf nodes represent files (storing SHA-256 digests); internal nodes represent directories recursively hashing sorted child digests.

Deterministic Internal Node Hash:
H(Dir) = SHA-256(H(Child_1) || H(Child_2) || ... || H(Child_k))
Subtree Duplicate Detection in O(1):

If two directory nodes share the exact same hash, the entire nested subtrees are identical. Detects directory clones in O(1).

O(log N) Incremental Snapshot Sync:

Diffing two snapshots traverses only modified branches in O(log N) rather than re-scanning the entire storage tree.

Advanced Data Structure 4

Binary Max-Heap Priority Queue & Pareto Reclamation

Max-Heap Algorithmic Mechanics

Storage Prioritization Metric:
PriorityKey = (cardinality - 1) · file_size

Ranks duplicate equivalence classes by total wasted physical storage.

Floyd's Linear O(N) Heapify:

Builds the binary heap in O(N) time using bottom-up sift_down operations on non-leaf nodes [N/2 down to 0], avoiding O(N log N) naive pushes.

Bounded I/O Top-K Extraction:

Under constrained I/O windows or cloud budgets, extract_top_k(K) retrieves the K highest-impact clusters in O(K log N) time.

I/O Optimization

Multi-Tier I/O Filtering Hierarchy

Tier 1: File Size Bucketing
O(1) Stat Inode Lookup
  • • Groups scanned files by st_size via stat(2).
  • • Buckets with cardinality = 1 contain provably unique files.
  • • Eliminates 2,346 files (24.7%) immediately on benchmark.
  • • Total physical disk byte reads required: 0 bytes!
Tier 2: 4KB Prefix Murmur3
O(4KB) Header Probing
  • • Reads only initial 4,096 bytes and computes 128-bit hash.
  • • Files with identical size but differing headers discarded.
  • • Pruned 2,060 candidate files without full file reads.
  • • Spares reading massive file bodies for header mismatches.
Tier 3: SHA-256 Digest
Full Cryptographic Fingerprint
  • • Computed only for files passing both Tier 1 and Tier 2.
  • • Evaluated on 5,104 files (avoided 4,412 files = 46.4%).
  • • Hardware-accelerated OpenSSL streaming in 64KB blocks.
  • • Pre-filtered keys probed against Bloom filter in O(k).

Data Integrity

Verification & Atomic Hard-Link Consolidation

Streaming Byte Verification

  • • Zero Collision Risk: Enforces streaming memcmp() byte verifier prior to linking, guaranteeing absolute safety against 2⁻²⁵⁶ hash collisions.
  • • Streaming 64KB Blocks: Reads canonical and duplicate files simultaneously in 64KB chunks to minimize RAM footprint.
  • • Early Exit: Aborts at the exact byte index of difference on mismatch.
  • • Empirical Validation: 3,092 byte verifications performed on benchmark with 100% confirmed matches (0 false positives).

Atomic POSIX Consolidation

  • • Atomic Inode Unification: Consolidates duplicate directory entries onto the canonical file's existing inode using POSIX link() + rename().
  • • Guaranteed Crash Consistency: Step 1: link(canonical, temp); Step 2: rename(temp, duplicate). If system crashes, original file remains intact.
  • • Transparent Access: Original directory hierarchies, filenames, and permissions are 100% preserved.
  • • Instant Kernel Storage Reclaim: Kernel reclaims duplicate disk blocks immediately upon link replacement (st_nlink increments).
