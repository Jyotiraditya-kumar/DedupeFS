Motivation & Problem Definition

Storage Redundancy & The Fundamental I/O Bottleneck

The Redundancy Problem

1. Storage Overhead from Duplicate Files:

Across user home directories, software repositories, and dataset storage, duplicate files commonly consume 20% to 50%+ of physical disk capacity.

2. Intractability of Naive Pairwise Checks:

Directly comparing all file pairs requires O(N²) comparisons. For 50,000 files, this requires >1.2 billion pairwise checks, causing severe disk thrashing.

3. I/O Bottleneck of Unfiltered Hashing:

Computing full cryptographic digests (SHA-256) on every file forces the OS to read gigabytes of data from disk, even though most files have unique sizes.

Proposed System Design

1. Multi-Tier Filtering Pipeline:

Tier 1 size grouping eliminates ~25% of unique files in O(1) time with 0 disk reads. Tier 2 tests 4KB Murmur3 prefix hashes to discard header mismatches early.

2. In-Memory Bloom Filter:

A dynamically sized bitset using Kirsch-Mitzenmacher double-hashing eliminates non-duplicate candidates in memory with Zero False Negatives (FN = 0).

3. Inverted Chained Hash Table:

Indexes duplicate candidates into equivalence classes in memory, enforcing load factor λ ≤ 0.75 via dynamic capacity doubling for amortized O(1) lookups.

4. Atomic POSIX Consolidation:

Consolidates duplicate directory entries onto a single canonical inode using POSIX link() + rename(), safely freeing duplicate blocks crash-safely.

Architecture & Pipeline

System Architecture & Processing Pipeline

1. Directory Traversal

Recursively scans target storage tree, tracking composite (st_dev, st_ino) keys to prevent circular traversal over symlinks and hard links.

2. Tier 1: Size Bucketing

Groups files by byte size via stat(2). Files with unique sizes are eliminated immediately with zero physical disk reads (~25% pruned).

3. Tier 2: 4KB Prefix Hash

Reads only the initial 4,096 bytes and computes 128-bit MurmurHash3. Mismatched file headers are discarded without reading entire file bodies.

4. Tier 3: SHA-256 Digest

Only candidate files sharing both size and prefix undergo full SHA-256 fingerprinting using hardware-accelerated OpenSSL streaming.

5. Bloom Filter & Hash Table

Queries optimal Bloom filter bitset in O(k) CPU operations. Candidate matches are inserted into the primary chained hash table.

6. Byte Check & Consolidation

Performs 64KB binary memcmp byte verification, then consolidates duplicates via atomic POSIX hard links (link + rename).

Probabilistic Filtering

Probabilistic Membership: Bloom Filter Design

Mathematical Formulation & Sizing

Optimal Bitset Size (m):
m = - (n · ln p) / (ln 2)²

For n = 100,000 files and p = 0.01 (1%), m = 958,506 bits (117 KB RAM).

Optimal Hash Probes (k):
k = (m / n) · ln 2 ≈ 7 probes
Kirsch-Mitzenmacher Double-Hashing:
g_i(x) = (h1(x) + i · h2(x)) mod m

Two 64-bit words from SHA-256 simulate k independent probes in O(1) CPU operations.

Zero False Negatives (FN = 0):

If any bit in g_i(x) is 0, the key was never inserted. Guaranteed no duplicate missed.

Observed Empirical Performance

Memory Footprint:

Consumes only 117.0 KB of memory for 100,000 files (1.17 bytes per file), fitting entirely in CPU cache.

Observed Saturation (Fill Ratio):

Fill ratio remains at ~1.46% to 4.0% across test runs, well below the 50% critical threshold where false positives escalate.

Empirical False Positive Rate:

Empirical FPR = 0.00% across all benchmark tiers (0 observed false positives among thousands of negative queries).

Primary Inverted Index

Index Structure: Hash Table with Separate Chaining

Table Architecture & Rehashing

Separate Chaining Design:

Array of bucket heads pointing to singly-linked list nodes. Each node stores an entry: (Hash256 key, vector<FileInfo> files).

Load Factor Threshold (λ ≤ 0.75):
λ = N / buckets (Capacity doubles when λ > 0.75)
Fast Power-of-Two Modulo:
bucket = hash & (capacity - 1)

Eliminates expensive CPU integer division instructions.

Memory Footprint:

Consumes ~4.2 MB total RAM for 23,380 entries, scaling linearly with dataset size.

Collision Dispersion & Chain Diagnostics

Empirical Load Factor:

Observed load factor λ = 0.384 across test runs (well below the 0.75 rehash threshold).

Maximum Chain Depth:

Longest bucket chain observed across 23,000+ files was only 3 elements, confirming near-optimal O(1) lookup.

Chain Variance (σ² = 0.26):

Low variance confirms cryptographic SHA-256 distributes keys uniformly without clustering into bucket hotspots.

Storage Reclamation

Safe Inode Consolidation via POSIX Hard Links

Two-Step Atomic Consolidation

1. Create Temporary Link:
link(canonical_path, temp_path)

Creates a new directory entry pointing to the canonical physical inode (st_ino).

2. Atomic Rename Replacement:
rename(temp_path, duplicate_path)

Atomically replaces duplicate path with the hard link in a single POSIX system call.

Crash Safety Guarantee:

POSIX rename() is atomic. If power fails mid-operation, either the original file or the new hard link exists—the path is never missing or unlinked.

Byte Verification & Safeguards

Streaming Byte Verification:

Performs 64KB binary memcmp byte-for-byte comparison before any link modification, eliminating hash collision risk.

Inode Cycle Detection:

Tracks composite 64-bit device-inode keys to detect filesystem circularity and prevent infinite directory loops.

Hard-Link Skip Logic (st_nlink > 1):

Detects files that already share an inode from previous runs and skips redundant consolidation.

Kernel Space Deallocation:

The OS increments st_nlink and deallocates duplicate physical disk blocks immediately.

Evaluation Methodology

Experimental Setup & Benchmark Datasets

Dual-Folder Testing Methodology

ground_truth/ (Untouched Reference):

Stores the pristine original dataset with independent physical inodes. Never altered during testing.

work/ (Active Test Directory):

Working directory where DedupFS runs scan and optimize operations.

Instant Work Directory Reset:

The active work/ directory can be restored from ground_truth/ in seconds via the UI or CLI for clean reproducible benchmarks.

Automated Verification:

A verification script performs bit-for-bit equivalence checks across all files to confirm zero file corruption.

Benchmark Dataset Tiers

Small Dataset (~280 MB, 9,516 files):

Resumes PDF corpus, Microsoft COCO images, curl source repository, and nested test archives.

Medium Dataset (~1.09 GB, 23,380 files):
